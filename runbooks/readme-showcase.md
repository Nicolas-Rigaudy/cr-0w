# README that sells (showcase a project)

Method used on the hub's own README. Reuse it per repo, one repo session each (`crow handoff`).

1. **Read first.** The repo's README, docs, tests and what it really does. Never claim a feature that is not built.
2. **Look at 3 or 4 popular repos of the same kind** (raw README from GitHub). Note: header, first screen, install placement, depth.
3. **Visuals before words.** Produce real screenshots from fixtures, never real data. TUI: `runbooks/tui-render.md`. GUI or shell: the repo's own screenshot script. Compress (`magick in.png -colors 128 PNG8:out.png`).
4. **Header options side by side.** Render 3 to 5 variants on a dark and a light background with `bin/crow-compare`; the owner picks. Use block letters or paths, not fonts, so it renders the same everywhere.
5. **Structure follows the genre found in step 2, not a fixed template.** The skeleton below (header and tagline, hero screenshot, one tight paragraph, a day-in-the-life list, a pain-to-benefit table, a short tour with one image per feature, honest setup steps, collapsible detail, license) is CR-0W's own, a dev-tool pitch. Do not reuse it elsewhere: the archeotech READMEs copied its headings and paragraphs and the owner rejected them as "literally all the same" (2026-10-23). Linux shells and rices (caelestia, end-4, Dux/DMS) use: centred name, palette-tinted badges, one showcase video before any prose, a short feature list, one-command install, usage/IPC, config in `<details>`, FAQ, credits to the configs they learned from, star history.
6. **Move depth to docs/** and link it. Keep the README skimmable.
7. **Audit pass.** Cut repeats of the same pitch, jargon (script names), and anything that overpromises (quick start that needs setup).
8. **Preview as GitHub renders it** (marked + github-markdown-css + mermaid in a local HTML) before committing.
9. **Prose rules:** short and declarative, no em-dashes, no "X, so Y", no "not X but Y", no AI mention. English for personal projects.
10. **Showcase video** (GUI shell): ONE short marketing video (about 45 to 60 s) that tours the important features with captions saying what is shown, not several clips. Smooth like the real desk (60 fps or more; caelestia's is about 144 fps), cursor visible, every change caused by a visible click or key, never by an IPC call that makes things happen on their own. Add-ons (archeotech theme packs such as Grimdark) stay out: show the base product. Headless capture below reached only 20 to 28 fps (2026-10-23, readback-bound, no VA-API driver), which the owner rejected as choppy. Mechanics, for stills and tests: `wf-recorder` + ffmpeg inside the repo's isolated headless session (check `which wf-recorder` at step 1; install is `sudo pacman -S`, which the owner runs in a real terminal, the `!` prompt has no tty for sudo). Raise the screenshot script's capture interval to lengthen its time budget. Write renders to `local/state/night/shots/`, and check `df -h /home` before long renders: a full disk shows up as silent PNG write failures. Never `rm -f dir/*` (blocked by the safety check): write to a fresh folder. Clean `/tmp/archeotech-shot.*` leftovers when done.
11. Commit as `chg[MD/SVG/PNG]: ...`; push only on the owner's OK (public repos).
12. **Name and identity.** Use the project's real name and its expansion/lore (ask the owner if unsure, e.g. CR-0W with a zero, not "crow"). Never draw pixel animals or mascots from scratch (a "crow" came out as a triceratops): prefer wordmarks, or a droid/robot motif the owner asked for.
13. **View every option image yourself** before presenting a comparison, and keep a single subtext line, no HUD or barcode clutter.
14. **Engine vs config.** In a public README, personal rules (commit format, push/merge policy, work/French conventions) are one configurable example set, never "how it works". Keep private routines (daily/weekly) in `local/`, ship generic examples.
15. **Handoff target.** Before `crow handoff`, ask where the repo is actually worked on (archeotech-shell is worked from archeotech-dotfiles). Keep generators (logo scripts) in the repo, not a scratchpad.

Portfolio level: a profile README (`<user>/<user>` repo) and pinned repos link the projects together. See the owner's thread on the personal site.
